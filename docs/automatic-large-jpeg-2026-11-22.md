# 大きなJPEGの表示用画像を自動生成する

## 目的と依頼の範囲

2026-11-22の所有者依頼は「元の写真を選ぶだけで、自動で表示用画像を作って安全に取り込めるようにする」、続いて「mainに統合できるところまで続けて」です。ローカル実装・試験・文書・レビューまでを対象とし、この依頼だけでmain統合・Push・Web公開は実行しません。

元写真の変更、原本保存、送信先追加、依存追加、DB v3/ZIP v2の変更、移行はありません。既存のPhoto/Thumbnail原子保存を使います。[O-06](open-questions.md)の端末別の長期予算はOPENのままです。

## 採用した方法と範囲

既存のファイル選択から、長辺の制限だけで拒否されるJPEGを専用Workerへ渡します。利用者が小さいコピーを用意したり、追加設定を選ぶ必要はありません。元の全バイト列からSHA-256、元Exifから日時・GPS・向きを取得し、表示用画像だけを生成します。内蔵プレビューへ置き換えないため、編集済み写真と古い内蔵プレビューの食い違いを避けます。

| 条件 | 今回の実装 |
|---|---|
| 新経路の入口 | 実署名JPEG、正の寸法、長辺が12000px超、総画素6000万以下、64MiB以下 |
| 対応するJPEG | 8bit、3成分、単一フレーム・単一スキャンのbaseline。progressive/multiscan/CMYK等は対象外 |
| 構造検査 | ヘッダー1MiB/256区画、画像終端、単一Exif APP1、TIFF参照・循環・項目数・容量を検査 |
| Exif予算 | TIFF 65527bytes、8IFD/256項目、値の合計65536bytes。読み取るのは元GPS/日時/向きの関連タグ |
| 同時処理 | 既存の入力合計64MiB予算内。復号予算60MPの全量を予約し通常復号とも排他、ページ内の自動Workerは同時1件 |
| ブラウザ機能 | Worker内のImageDecoderとOffscreenCanvas。希望サイズ512pxで復号を要求 |
| 返却Frame | coded/display両寸法の各辺8192以下・積100万以下、visibleRect一致、Exifに対応する向きを検証 |
| 保存する画像 | 長辺512px以下、JPEG品質0.82、1MiB以下。メイン側でも形式・寸法・スキーマを再検証 |
| 期限 | Workerの作成から返却検証まで5秒。timeout/通信異常では終了して全体を中断 |

`inspectImage()`とZIPの画像検証は緩めていません。従来受理されるJPEGは従来経路のままです。たとえば長辺12000px以下・80MPの写真は従来同様の写真情報のみ保存になり得ます。長辺12000px超・64MPは今回は拒否します。

試作では16000×4000px（64MP）の生成にも成功しましたが、製品では元の復号画素予算60MPを拡大しません。64MP以上まで対応する案は今後の別判断です。上限の一律緩和、原寸Canvasへのfallback、追加デコーダー導入は採用していません。

## 成功・失敗・中断

- 成功は従来と同じ「追加」。原本のハッシュ・バイト数・元Exifと512px画像を保存し、原本バイト列をDB/ZIPへ残しません。
- 未対応のブラウザ/保存形式、過大Frame、不正構造は「失敗」と理由を表示し、次の写真へ進みます。新経路の失敗を写真情報のみ保存へ落としません。従来のHEIC等の部分成功は維持します。
- timeout/Worker異常/不正応答では、その回の処理を止め、以後の取り込みをページ再読み込みまで拒否します。Jobをinterruptedとして保存・通知しようとしますが、Job書き込み/通知も失敗した場合は確定を保証しません。再読込必須の主エラーを維持し、二次失敗はcauseに保持します。
- 稼働中の自動Workerを利用者が中断した場合も、再読み込みを案内します。Worker開始前・通常経路だけの中断はこの制限を追加しません。Job失敗等で稼働中Workerを回収する場合も再読込案内を維持します。
- 保存直前の重複照会から戻った後にも停止/中断を確認します。保存開始前なら追加しません。開始済みのDB保存は確定し得るため、追加済みの写真は保持します。
- 重複は復号前・入力順の保存直前・保存トランザクション内で確認します。元写真の選び直しで、既存の失敗サムネイルを再生成する機能ではありません。

## 安全性の限界

希望サイズや返却Frame上限は、ブラウザ内部のメモリー使用量のハード上限ではありません。5秒は応答期限であり、Worker終了の瞬間にnative処理の停止・メモリー解放が完了した保証でもありません。終了後の自動再試行を避け、元の画素予算を保った限定導入とします。再読み込みも物理メモリーの即時解放を保証する説明には使いません。

実際にエラーが出た利用者の画像・寸法は未確認です。この実装でその写真を必ず取り込めるとは断定しません。全形式・全ブラウザ・低メモリー端末・任意の不正画像への完全な安全性は未確認です。

### nativeメモリーの実測（Windows・隔離Chromium 159.0.8154.6 / revision 1255）

PillowのRGB疑似乱数画像（seed 20261122、JPEG品質20、baseline）をローカル生成しました。通常48MPは8000×6000、追加経路48MPは16000×3000、60MPは16000×3750です。各ケースは新規ブラウザで12枚×3バッチ、COMコメントで元SHAを変えています。計108枚すべて追加成功。元ファイルはそれぞれ9503419 / 9511832 / 11894445bytesです。

CDP `SystemInfo.getProcessInfo`で当該ブラウザのみのPIDを列挙し、常駐PowerShellのProcess.Refresh後のWorkingSet64/PrivateMemorySize64を目標20ms間隔で採取しました。通常Chrome等のPIDは対象にしません。採取件数は322 / 244 / 273。実際の採取間隔は実行環境に依存します。

| ケース（各36枚） | 同時採取WorkingSet合計の最大 | Private bytes合計の最大 | 3バッチ終了後のPrivate bytes |
|---|---|---|---|
| 通常48MP | 約570MiB | 約421MiB | 約169MiB |
| 自動48MP | 約435MiB | 約209MiB | 約150MiB |
| 自動60MP | 約609MiB | 約234MiB | 約174MiB |

WorkingSetは共有ページを二重計上し得るため専有量ではなく、短い瞬間ピーク/VRAMの完全な測定でもありません。60MPケースのWorkingSetは約367MiBの開始時点から終了後約584MiBまで増加しており、長時間のメモリー安定性・リーク不存在は主張しません。Private bytesも解放時期を保証する指標ではありません。この測定は安全上限の引き上げや一般端末への保証の根拠にしません。
