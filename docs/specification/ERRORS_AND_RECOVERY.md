# エラー・復旧

根拠: [ErrorNotice](../../src/presentation/error-notice.ts)、[app.ts](../../src/presentation/app.ts)、[storage.ts](../../src/infrastructure/storage.ts)、[所属編集](../../src/presentation/visit-photo-editor.ts)、[写真側所属編集](../../src/presentation/photo-album-editor.ts)、[archive.ts](../../src/infrastructure/archive.ts)。

## 障害ごとの動作

| 状況 | 現行の案内/保護 | 次にできる操作 |
|---|---|---|
| DBを開けない/初期読込失敗 | 基本画面に案内。初期化完了までworkspaceをinert/disabledにする | 保存領域設定/空き容量を確認し再読み込み。DB削除/自動リセットはしない |
| 他タブがアップグレードをブロック | `onblocked`でほかのPhoto Routeタブを閉じる案内 | ほかのタブを閉じて待つ。進行中のopenはその後続行可能 |
| 別タブのversionchange | 接続をcloseし、書き込み操作を無効化、未保存状態確認後の再読み込みを案内 | 未保存入力を確認してから再読み込み |
| 容量不足 | `storageErrorText`が原因チェーン中のQuotaExceededErrorを検知し、基本画面のDB案内へ集約 | 空き容量/ブラウザ制限を確認。保存結果を確認してから次操作 |
| データ再取得の失敗 | `render()`側のエラー案内、未保存内容がある場合は再読み込みを制限する条件あり | 読み込みだけの再試行と保存再送を区別 |
| 背景地図スタイル/広範なタイル失敗 | 地図エラーと再試行。一覧/バックアップは継続利用できる | 同じOpenFreeMapスタイルを再取得。写真/所属の再保存ではない |
| 地図初期化失敗 | 地図以外が使えることを案内。初期化失敗は再読み込み入口 | 編集中/保存結果不明を先に確認 |
| 画像検証/サムネイル失敗 | ファイル単位のfailed/partialと理由。処理済み枚数を報告 | 正しいファイル/容量条件を確認。既存保存済み写真を消さない |
| 所属競合 | 全件保存を中止し、ドラフト保持。確認画面を閉じても理由/最新状態確認入口を残す | 最新状態確認、編集復帰、明示的破棄を使い分ける |
| 所属保存の応答喪失 | operationIdを照会。appliedのみ成功として反映 | unknownのまま成功表示/盲目的再送をしない |
| 旅行/アルバム作成の応答喪失 | 作成開始時のID/対象Tripを保持し、DB内の存在/内容を確認する経路 | 同じ対象を確認。結果不明のまま別IDで重複作成しない |
| 未保存補正/名前/所属 | 離脱確認や保存中/結果不明の閉じる制限 | 編集継続、保持して移動、明示的破棄など、各画面の選択肢に従う |
| ZIP破損/不正参照 | 検証前にDBを変更しない。衝突は既定拒否 | 別の正常ZIPを選ぶ。破損を無視して投入しない |

DB案内を地図案内より優先し、同じ障害を大量のモーダルで重ねません。モーダル表示中は案内をその内部へ配置します。詳細は展開可能で、通常時はエラーUIを表示しません。

## 再試行の境界

**再実行できる操作**: 読み取り、地図スタイル取得、ZIPの検証、operationIdによる状態照会。いずれも既存の画面状態/未保存保護を通します。

**無条件再送してはいけない操作**: 保存結果不明の所属保存、作成、取り込み、復元、ごみ箱移動等。UI上のエラーは「何も保存されなかった」証拠とは限りません。保存トランザクション後に再描画やジョブ更新だけが失敗する可能性もあります。状態/対象IDを確認してから進めます。

## 内部Undoとごみ箱

Undoは内部APIとして残りますが、一般UIの復旧入口はごみ箱からの復元です。通知/ショートカット等を独断で再追加しません。`undoLatest(expectedId?)`を使う将来の変更は、同一トランザクション内の期待ID/全状態比較を維持する必要があります。実行不可の履歴は保持します。

Tripのごみ箱移動は子を表示から隠す操作で、写真原本を削除する操作ではありません。写真/アルバムの復元でTripが削除済みなら、先に旅行を復元します。写真/アルバムのリンク/サムネイルは保持されます。

## 利用者向けのバックアップ・移行・復旧手順

1. 更新前に現在のアプリからZIPを書き出し、保存されたファイルを別の保管先へ確保する。元の高解像度写真も別に保管する。
2. ZIPが読めることを、**空の専用ブラウザプロファイル/別オリジン**で検証・復元し、件数、サムネイル、代表的な日時/GPS/所属を確認する。元の環境を初期化しない。
3. 更新前後はほかのPhoto Routeタブの未保存内容を確認して閉じる。DB更新待ちをDB削除で解消しない。
4. 更新後データが見えない場合、URLのホスト/ポート/HTTPS、ブラウザ、プロファイル、選択旅行、検索/限定モードを確認する。保存領域が消えたと断定して新規取り込みを重ねない。
5. 復元は空の安全な別環境を先に使う。同じIDの異なる内容がある場合は既定拒否。明示的な「別コピー」は新IDのデータを追加するので、何度も繰り返して増やさない。
6. IndexedDB v3は旧v2アプリからそのまま開けず、ZIP v2も旧アプリで読めるとは限らない。旧版へ戻す必要がある場合は、更新前ZIPと旧環境を独立保全し、逆移行が実装済みとは考えない。
7. 公開HTTPSサイトへ移る場合、ローカルと保存領域は別なのでZIPで移行する。ブラウザ/ストレージ全消去、元写真削除、既存DBへの強制上書きは復旧手順に含めない。

内部のbefore/after履歴は同じ端末のDBにあり、端末故障・ブラウザデータ消去への外部バックアップにはなりません。
