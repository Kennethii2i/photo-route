# 旅行名とごみ箱の完全削除

## 依頼と所有者承認

2026-11-23、所有者が同名旅行を許容する問題、ごみ箱からの削除不足、削除前の確認画面を依頼した。Mainが次の具体案を提示し、所有者は「この安全策で実装する（推奨）」と回答した。

> ごみ箱の項目ごとに確認画面を出し、削除対象を含む最新のZIPを利用者が再選択して検証できた場合だけ実行する。旅行は中の写真・アルバムも削除、アルバムは写真を残し、写真はサムネイル・所属も削除する。途中の失敗は全体を取り消し、削除後はZIPから復元する。既存の操作履歴は保持し、削除対象をUndoで復活させない。元写真ファイルは削除しない。

開発・隔離試験が対象で、main統合/Push/Web公開/実DB操作はこの承認に含まない。長期保持/自動消去のO-12を一括APPROVEDにしない。

## 実装と受け入れ条件

- 新規旅行はtrim後の同名（ごみ箱含む）を同一readwriteトランザクションで拒否。case-sensitiveで文字幅/内部空白を正規化しない。既存重複・旧ZIP復元の互換性を維持し、自動改名/統合しない。
- ごみ箱各行の復元と完全削除を分ける。確認画面はキャンセル初期フォーカス、対象名・削除範囲の件数、ZIPを再選択する入口、原本非削除と復旧の説明を持つ。最新全体ZIPを照合するまで削除無効。
- Storageが発行した不透明な計画だけを受け付け、ZIPと全体SnapshotのサムネイルSHAまで照合。削除時にSnapshotの5ストアの指紋を同一transactionで再検査し、別接続の変更を拒否する。計画は発行後に再利用しない。
- 旅行は全子を削除、アルバムは写真を残し、写真は所属/サムネイルも削除。残存Visitの旧代表写真参照は壊さず拒否。別旅行・別アルバムの写真/所属を保持する。
- 途中のdelete失敗は全体abort。応答喪失は前後指紋を照会し、結果不明なら理由と再送禁止を表示。確定後のrender失敗は削除失敗と言わない。
- recovery/jobsは保持し過去の名前・写真情報が残る。内部Undoの期待値比較・operationId契約を変更しない。元写真ファイル/DB v3/ZIP v2/依存/通信先は変更しない。

実装: [storage](../src/infrastructure/storage.ts)、[削除範囲](../src/infrastructure/trash-deletion-plan.ts)、[ZIP](../src/infrastructure/archive.ts)、[確認画面](../src/presentation/trash-deletion-dialog.ts)、[画面接続](../src/presentation/app.ts)。

## 復旧と制約

検証したZIPで既存の追加型復元を行う。旅行全体を削除した場合は元IDで戻せる。写真/アルバムだけでは残存旅行と衝突するため「別コピーとして復元」で旅行全体を別IDへ戻す場合がある（既存方式では名前に「復元コピー」が付く）。部分マージ/上書きは追加しない。ZIPに操作履歴/jobs/原本は含まないが、それらの履歴は削除処理でも変更しない。

最新全体ZIPが既存の件数/容量上限に収まらない場合は削除を拒否する。対象旅行のrunningジョブも拒否し、以前から残るジョブを黙って修正しない。保持された履歴の情報まで消去する機能ではない。一括空化/自動消去は対象外。
